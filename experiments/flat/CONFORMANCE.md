## Verification note: four distinct levels, not a single pass/fail

Every fixture in the table above is checked at four independent
levels, and the table deliberately keeps them separate rather than
collapsing to one verdict:

1. **Python oracle** (`run_python.py`) — always runnable here, no
   toolchain dependency.
2. **Go implementation** (`spherepop-go/`) — a working `go` 1.22
   toolchain is present in this environment, so `spherepop-go`'s own
   `cmd/fixtures` runner was built and run natively, with no workaround
   needed. This is the only non-Python column in this table obtained
   from an ordinary, unmodified build.
3. **Rust kernel** (`spherepop-kernel/src/bin/fixtures.rs`) — this
   sandbox has no working system `cc`/`ld` (Ubuntu Core / snap-confined,
   no `apt`/`sudo` package install available), so the table's automated
   `cargo run` step shows `?` (blocked). A genuine linked-and-run Rust
   result was separately obtained via a **static-musl / `rust-lld`
   workaround** described below; that workaround is not wired into the
   generator script itself, so it is recorded here in prose rather than
   the generated table. It is **not** a claim about the project's
   required or preferred build environment, which remains an ordinary
   `cargo build` with a system linker wherever one is available.
4. **C kernel** (`compiler/tools/fixtures/main.c`) — no C compiler of
   any kind (`cc`/`gcc`/`clang`/`tcc`/`zig`) exists in this environment,
   and unlike Rust there is no bundled, linker-independent fallback for
   C. Cells for this column are marked `BLOCKED`/`?` ("not run"), never
   a failure — the code was reviewed by hand where relevant, but
   nothing here should be read as a C-side pass or fail.

### Reproducing the Rust musl/`rust-lld` build used for verification

```bash
cd spherepop-kernel
rustup target add x86_64-unknown-linux-musl  # if not already installed
LLD="$(rustc --print sysroot)/lib/rustlib/x86_64-unknown-linux-gnu/bin/gcc-ld/ld.lld"
RUSTFLAGS="-C linker-flavor=ld -C linker=${LLD} -C target-feature=+crt-static" \
  cargo build --target x86_64-unknown-linux-musl --bin fixtures
./target/x86_64-unknown-linux-musl/debug/fixtures ../experiments/flat/fixtures
```

This bypasses the missing system `cc`/`ld` by linking with the
`rust-lld` linker already bundled inside the active rustup toolchain,
and links libc statically (`+crt-static`) against musl so no dynamic
system libraries need to be located. It was used to confirm, with a
genuine linked binary rather than a `cargo check` type-check, that:

- `08_meld`'s executable `history_a`/`history_b` schema (added in an
  earlier session) passes on Rust, not only on Python.
- The `13a`/`13b` quotient-equality pair (added in this session, see
  below) passes on Rust, not only on Python.

No kernel or runner source changes were needed for either result — the
Rust code already implemented everything both fixtures exercise; only
the build/link procedure needed a workaround for this sandbox.

## `13a`/`13b`: a canonical quotient-equality fixture pair

`13a_quotient_equal_different_history_run_a.json` /
`13b_quotient_equal_different_history_run_b.json` were added to witness
$H_1 \neq H_2 \land C_c(H_1) = C_c(H_2)$ for $C_c$ = `collapse_quotient`
(union-find over non-`__meta__` Binds) — a strictly different, and
strictly weaker, invariant than the `05a`/`05b` pair, whose Omega
*snapshots* agree but whose `collapse_quotient` classes for (3, 4)
actually *disagree* (05a Binds 3–4; 05b only Refuses 3). No new op
kinds, event fields, or expectation keys were introduced — both
fixtures use only the existing `pop`/`refuse`/`bind` ops and the
existing `quotient_same_class` expectation already exercised by other
fixtures, so no kernel/runner code changes were required in any of the
implementations.

With this pair now passing on Python, Go (natively), and Rust (via the
musl workaround), the canonical suite demonstrates
$H_1 \neq H_2 \land C_c(H_1) = C_c(H_2)$ as an independently-executed,
three-implementation result. It still does not test `personalinks`'
named `history_view`/`extensional_view` functions — that remains a
separate, lineage-specific API gap, not a missing canonical invariant,
and should not be conflated with the abstract quotient-equality result
now demonstrated here.

The C cells for all fixtures remain `?`/`BLOCKED` (not run) for the
reason given above. Re-run `cd compiler/tools/fixtures && cmake ..
&& make` (or `./run_all.sh`) in an environment with a working C
compiler to regenerate those cells.

## Blocked adapters

### SphereForth (prototypes/sphereforth_gforth.zip)

No longer blocked as of this session — see the `prototypes/sphereforth_gforth.zip` entry in `IMPLEMENTATIONS.md`. The normal `gforth` (snap) invocation still fails here ('cannot join mount namespace of pid 1'), and the default startup image still can't build its FFI C shim (no `cc`/`libtool`), but invoking `gforth-fast` directly with the bare/minimal bootstrap image (`--image-file=.../kernl64l.fi`) skips that bootstrap and runs. Doing so surfaced seven genuine, pre-existing bugs in `log.fs`/`sym.fs`/`ops.fs`/`repl.fs` (stack-argument-order errors, a non-escaping-`S"` misuse, and a malformed pictured-numeric-output call), all fixed and verified: the shipped `demo.fs` and `REPLAY` now run to completion with the expected output. The interactive `run` loop in `repl.fs` remains unverified — this bare-kernel image's `refill` does not read piped stdin, which looks like a further consequence of the workaround image itself rather than a SphereForth bug. This adapter is not wired into `generate_conformance_matrix.py` (no shared fixture format exists for it yet), so it isn't in the generated table above.
